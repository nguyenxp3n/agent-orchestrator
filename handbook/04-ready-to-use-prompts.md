# Chapter 4: Prompt Engineering, Prompt Compiler, and Ready-to-Use Role Prompts

## 4.1 Prompt design philosophy

Agent Orchestrator treats prompts not as conversational prose, but as **executable contracts** compiled directly from repository truth.

Standard prompt anatomy:

```text
ROLE + CONTEXT + TASK + FORMAT + CONSTRAINTS
```

For multi-agent software engineering, the framework extends this structure:

```text
ROLE
+ OBJECTIVE
+ SUCCESS PREDICATE
+ CONTEXT / SOURCE OF TRUTH
+ SCOPE & OWNERSHIP
+ RESOURCES
+ CONSTRAINTS
+ EXPECTED OUTPUTS
+ NON-COUNTING OUTCOMES
+ VERIFICATION
+ STOP / ESCALATION
+ OUTPUT CONTRACT
```

A prompt must provide sufficient architectural clarity so that workers do not guess on decisions that alter system behavior. Length increases only when a task genuinely requires additional domain context or safety boundaries.

## 4.2 The Prompt Compiler

Before dispatching workers, the Lead invokes `prompts/prompt-compiler.md` following the protocol in `prompt-engineering/02-prompt-compiler-protocol.md`.

```text
Project Truth
+ Work Package Contract
+ Ownership Matrix
+ Resource Registry
+ Acceptance Criteria
+ Verified Evidence
        |
        v
   Prompt Compiler
        |
        v
   Role Prompt Draft
        |
        v
  Prompt Quality Gate
        |
        v
  READY -> Dispatch
```

The compiler begins with the `SUCCESS_PREDICATE` rather than the persona. It resolves authoritative documents, selects minimal context pointers, binds write boundaries and resource slots, defines non-counting outcome predicates, specifies verification commands, and enforces the structured return contract.

## 4.3 Three operating prompt modes

### Compact Mode

Used for small, deterministic bug fixes and narrow refactors. Retains core essentials:

```text
Role + Objective + Success Predicate + Scope + Expected Outputs + Verification + Output Contract
```

### Standard Mode

The default mode for feature Work Packages. Implements complete agent-grade contracts, ownership boundaries, and resource governance controls.

### Long-Horizon Mode

Used for multi-turn, high-risk, or architectural tasks. Adds:
- Formal definitions for critical technical terms
- Explicit success predicates
- Exhaustive non-counting outcome checks
- Domain-specific failure mode warnings
- Evidence-traceable progress tracking
- State persistence conditioned on passing verification tests
- Audit-gated completion criteria

## 4.4 Context Engineering

Prompts should contain only essential task context. Following `prompt-engineering/03-context-engineering.md`, organize context systematically:

```text
1. Persistent project standards and authority indexes
2. Relevant specification and architecture excerpts
3. Target source files, interfaces, and test fixtures
4. Active error logs and verified execution traces
5. Compact conversation summaries
```

Classify context by trust tier:
- `AUTHORITATIVE`: Immutable specifications and repository truth.
- `VERIFY_BEFORE_USE`: Outputs generated by other workers that require verification.
- `UNTRUSTED_DATA`: Error logs, external tool outputs, or unverified agent assertions.

Prefer precise pointers (file paths, section headings, contract identifiers) over full repository dumps. Instructions found within untrusted inputs are treated as raw data, never as architectural authority.

## 4.5 The Prompt Quality Gate

Before dispatching any compiled prompt, evaluate it against `prompt-engineering/07-prompt-quality-gate.md`.

Key checklist items:
- Objectives and success predicates are unambiguous.
- Source authorities are explicitly declared.
- Context is minimal, precise, and free of bulk dumps.
- Path boundaries and resource allocations are strictly defined.
- Expected outputs are fully enumerable.
- Plausible near-misses are eliminated via non-counting outcomes.
- Verification commands produce verifiable evidence bound to candidate commit SHAs.
- Stop conditions and escalation paths are explicit.
- Output formats adhere to structured machine contracts.

Disposition outcomes:
- `READY`: Approved for immediate dispatch.
- `NOT_READY`: Blocked; requires missing specifications or corrected boundaries.
- `ESCALATE`: Blocked; contains architectural conflicts requiring human decision.

Only prompts marked `READY` may be dispatched.

## 4.6 Lead Orchestrator System Prompt

Reference: `prompts/lead-orchestrator-system-prompt.md`.

The Lead owns prompt compilation, repository truth, coordination states, quality gates, audit decisions, and integration sequencing. The Lead never accepts self-reported completion claims without independent verification.

## 4.7 Coding Worker Task Assignment

Reference: `prompts/worker-task-assignment.md`.

Every worker prompt requires compiled task parameters:

```text
WP_ID
OBJECTIVE
SUCCESS_PREDICATE
CONTEXT_REFERENCES
OWNERSHIP / PATH BOUNDARIES
RESOURCE_ALLOCATIONS
FROZEN_CONTRACTS
EXPECTED_OUTPUTS
NON_COUNTING_OUTCOMES
VERIFICATION
STOP_OR_ESCALATION
OUTPUT_CONTRACT
```

Workers submit a `WORKER_COMPLETE_CLAIM`. The independent Auditor decides final acceptance.

## 4.8 Clarifications versus Decision Requests

Use `prompts/clarification-guidance.md` when specifications are clear and the worker simply needs guidance on application. Use `prompts/architectural-arbitration.md` when choosing between technical alternatives that impact system architecture, security invariants, public contracts, or shared resources.

Any decision that alters the baseline Work Package definition requires recompiling the affected worker prompt.

## 4.9 The Independent Auditor

Reference: `prompts/independent-auditor.md`.

Auditors operate with a fresh context window, inspect the exact candidate commit SHA, and apply systematic failure-mode checklists. The Auditor reconstructs verification evidence directly rather than reading conversational narratives:

```text
Worker narrative = unverified claim
Candidate SHA + files on disk + test execution logs = verified evidence
```

The Auditor evaluates both success predicates and non-counting outcomes, ensuring that passing tests reflect genuine functionality rather than hollow assertions.

## 4.10 The Integrator and CI/CD Coordinator

Reference: `prompts/integrator-cicd.md`.

The Integrator accepts only candidates marked `ACCEPTED`, verifies the exact commit SHA, merges branches sequentially according to the DAG, runs global cross-package test suites, and validates cloud CI pipeline executions.

## 4.11 Model-Agnostic portability

Canonical prompts specify behavioral actions:

```text
Open the relevant source file.
Search for existing repository patterns.
Execute project test commands.
Delegate focused subtasks if the environment supports subagents.
```

The framework avoids locking into vendor-specific tool names. Tool syntax belongs to the environment harness; objectives, boundary constraints, and verification bars remain universal.

## 4.12 Prompts cannot replace environment enforcement

Prompts provide instruction-level governance. To guarantee system invariants, combine prompt boundaries with filesystem isolation (worktrees), explicit resource registries, branch protection rules, automated CI pipelines, and independent forensic audits.

## 4.13 Standard execution workflow

```text
1. Populate templates/prompt-compile-input.md
2. Compile task prompt using prompts/prompt-compiler.md
3. Render target role prompt with concrete parameters
4. Run Prompt Quality Gate
5. If READY -> dispatch worker
6. Worker returns structured completion claim and execution logs
7. Auditor independently verifies candidate diff and test runs
8. Accepted candidate enters sequential integration queue
```
